PM Simulation — Architecture

A deterministic, SQLite-backed simulation of a software team's work week (Mon 09:00 → Fri 17:00). NPC coworkers work a Jira board over simulated time; a PM agent-under-test observes and steers them through Slack.

1. Overview & repo layout

Everything lives under pm/. The design has three central invariants:

  • SQLite is the single source of truth. Each run owns runs/<id>/world.db (live state) plus an immutable seed.db snapshot, so runs are replayable and gradable.
  • Only the engine mutates the world. All writes go through the typed Store, driven either by Engine.perform_action (agent tools) or by an event's start()/done() hooks.
  • Determinism. Event ordering is (start_tick, seq), NPC randomness is seeded, and time only moves through the engine — never a background thread.

3. The clock pm/sim/clock.py

Sim-time is measured in integer ticks — one tick is one simulated minute — persisted in meta.current_tick, so time survives save/resume and is fully decoupled from wall-clock (one agent action may cost many ticks regardless of how long the model took to decide).

The calendar is work-hours only: time exists during 09:00–17:00 on weekdays. Nights and weekends don't exist in tick space — 17:00 rolls straight into the next 09:00, so a delay that crosses 5pm lands the next morning automatically.

  • Module helpers — hours(n), days(n), weekday(tick), hh_mm(tick), is_within_week(tick), format_tick(tick) → "Wed 14:30".
  • SimClock(store) — now() reads the tick, advance(delta) writes it (delta must be non-negative: time never runs backwards), as_clock_str() renders it. The only mover of the clock is the engine.

4. Events pm/sim/events.py

An Event is a fact on the world's timeline — something that happened or is scheduled to happen: chat latency, a message read, a meeting, being out of office. The event table is that timeline in both directions — pending rows are the future, done rows plus the event_log are the immutable record — making it simultaneously the calendar, the message bus, and the ledger. Each event is one object with a uniform lifecycle and exactly one row (completion is a status flip on that row, not a second record); the engine rehydrates the right subclass from a DB row via EVENT_REGISTRY.

Scheduling & calendar (contention)

Engine.schedule — pm/sim/engine.py

  • The event table is the queue — no parallel in-memory heap, no separate scheduler component: queueing lives on the engine.
  • schedule(event) rejects past start ticks, stamps a monotonic seq (resumed from max_event_seq()+1) and created_tick, persists, then calls calendar.reserve.
  • Queue order is (start_tick, seq) — deterministic across replays.

Calendar — pm/sim/calendar.py

  • Durative events occupy their people in the occupancy table; a meeting occupies all attendees + organizer, work occupies its single actor.
  • Yield: the incoming event's start is pushed past any overlapping block of ≥ priority.
  • Bump: lower-priority overlaps lose — an active one pauses and resumes (duration += incoming.duration); a pending one moves after the window and re-reserves recursively.
  • All resolution happens at reserve time — the engine has no runtime preemption. Instantaneous events reserve nothing and are never blocked.

5. Sim work: the sync / async boundary pm/sim/engine.py

The engine owns the event queue and time progression (there is no separate scheduler component), and this is the deliverable's central systems choice: agent actions are synchronous, the world is asynchronous — but both move the same single clock. No background threads exist anywhere.

Synchronous — perform_action(actor, cost, effect)

The contract every agent/Jira mutation routes through:

  • Run effect() at the current tick — no sim-time passes while it runs.
  • Log an action entry for the actor.
  • advance(cost) — then return the events that transitioned during the advance, so the caller observes what the world did in response.

Asynchronous — step()

Advance exactly one simulated minute:

  • activities.tick(now) first — work ending at this minute completes (firing on_activity_done) before anything that begins at it, so a zero-slack schedule strands nothing at meeting boundaries,
  • then start() every pending event whose start_tick has arrived,
  • then done() every active event whose duration has elapsed (freeing its occupancy blocks).

advance(minutes) just loops step(); an instantaneous event starts and finishes within one tick.

The week loop — pm/sim/simulation.py

while not sim.is_over():          # now < WEEK_END_TICK (2400)
    on_tick(sim)                  # hooks read state + schedule(); must not advance time
    sim.step()                    # engine advances one minute
# terminal "week.end" log → RunSummary(final_tick, events_fired)

Simulation adds week guardrails on top of the engine: events that would start at or after Fri 17:00 are dropped (logged as event.dropped_past_week), and perform_action costs are clamped to the remaining week.

6. Activities pm/sim/activity.py

An Activity is the durative-work system NPCs actually run on. Where an Event is a fact on the world's timeline, an Activity is a thing one or more NPCs are doing right now — it burns down minute by minute, can be interrupted by something more important, and resumes with its remaining time frozen. The activity table is each NPC's attention scheduler: at most one started activity per person, with their backlogged and interrupted items queued behind it by priority. (The pool of candidate work lives on the Jira board — a WorkDriver sweep is what commits a candidate into someone's attention as a jira_work activity.) The table is created idempotently by ActivityManager; effects are kind-specific side effects on start/done — jira_work tracks the Jira issue named in its params and applies the same transitions JiraTicketEvent does.

Manager rules (ActivityManager): each NPC is in at most one started activity across all attenders; dispatch runs highest-priority first; an incoming activity waits if any attender is already in an equal-or-higher-priority activity, and interrupts strictly-lower ones (every activity is interruptible). Priority is the only per-kind knob besides the two effect hooks — adding a kind is one registration in ACTIVITY_KINDS. The manager also exposes one seam: on_activity_done, fired once per completed activity from tick() (after the burn loop, before re-dispatch) — the runner installs the WorkDriver's sweep there.

This is the live path for NPC work: the scenario catalog dispatches every ticket as a jira_work activity, and meetings/OOO reach in as bridged meeting / ooo activities. Events remain the system for scheduled occurrences (meetings, OOO, communication latency) and for the procedural generator's JiraTicketEvent path.

7. How events, actions & activities trigger each other

The mental model: events are the world's timeline (what happened or is scheduled — the calendar, the message bus, and the ledger in one table) and activities are each NPC's attention (one started thing per person, queued behind by priority). An NPC lives in both planes at once — events involving them fire while they work (reading Slack costs no attention), and the bridge is the one place a timeline fact seizes attention directly. In one sentence: events happen on the timeline → completions poke the NPC (on_event_done) → the NPC commits attention (request) or speaks (schedule) → finished activities poke it again (on_activity_done).

Three moving parts share the single clock, and each fires the others:

  • Activity done → NPC behavior → next activity or event. NPC work runs as jira_work activities; nothing polls. When an activity completes, ActivityManager fires on_activity_done, where the WorkDriver sweeps the roster: every member with nothing in flight requests their next issue as a new activity (one completion can unblock anyone), and an announces_progress persona also triggers a status SlackSendEvent. The only other dispatch is the kickoff sweep at week start. An activity belongs to its NPC attenders (≥ 1) and occupies them — one started activity per NPC is exactly what interrupt/resume arbitrates.
  • Action → events. An action (Engine.perform_action) runs its effect at the current tick, then advance(cost) loops step(). The agent's send_slack uses its tool to trigger an event: the effect schedules a SlackSendEvent, which lands through the event pipeline during the cost window — the same path NPC messages take, so world reactions fire for it too.
  • Event done → reactions; meetings preempt work. When step() completes a standup or a Slack send, the close reactions fire (WorkDriver.on_event_done, the Engine's event-completion hook — the NPC component never touches the Simulation loop): naming a person closes their in_review work, then the driver re-sweeps so unblocked dependents dispatch immediately. A MeetingEvent starting requests a bridged meeting activity that interrupts its attendees' work (OOO bridges at priority 200).

How traits become behavior

WorkDriver — pm/sim/npc.py

The single, completion-driven dispatch path:

  • sweep(engine) — every member with nothing in flight picks their next issue; plain-id members work a pre-assigned board, CastMembers also pull unassigned discipline work (self-assigning; works=False skipped). Run once at kickoff, then from on_activity_done on every completion.
  • _next_issue — an issue at priority ≤ 0 (a PM “pick up” directive) overrides everything; else freestyle picks seeded-random (Random(f"{seed}:{pid}:{now}")), else by priority.
  • _dispatch_issue — requests a jira_work activity (duration = estimate_minutes, auto_close from the persona) plus an optional SlackSendEvent status if announces_progress.

Reactions — pm/sim/npc.py (same component)

One handler per EventType, fired when an event completes; WorkDriver.on_event_done is installed on the Engine — closes, then a sweep:

  • MEETING done → a standup prompts attendees to close their in_review work.
  • SLACK_SEND done → a message naming a person closes their in_review work; a “pick up KEY” directive bumps that issue to priority 0.
  • JIRA_TICKET done → the assignee picks up their next ready ticket (the event-path cascade — the procedural generator's flow).
  • Email/Slack reads and OOO are documented no-op placeholders.

9. The PM agent ↔ the sim pm/agent/

The PM cannot touch the board directly. Its only mutation is Slack — and the world already reacts to Slack (reactions._on_slack_send), giving the agent exactly two levers:

  • Close: a message naming a person closes their finished-but-unclosed (in_review) work — which can unblock a teammate's dependent ticket.
  • Direct: “please pick up KEY next” bumps that issue to priority 0 — the level even a freestyle persona works first.

10. Persistence & scenarios

Store & schema — pm/db/

Database is the only module touching sqlite3 (Row factory, foreign keys ON, WAL, online backup_to). Store is the single typed interface on top — no raw SQL leaks past it. Schema (version 2) highlights:

  • Sim machinery — meta (KV: current_tick, seed, scenario), event (the durative queue itself, indexed on (status, start_tick, seq)), event_log (append-only trace), occupancy (per-person calendar blocks).
  • World entities — person (persona JSON, delay bounds), project, channel/message, email thread tables, meeting/meeting_attendee, transcript (available_tick gates discoverability; every meeting leaves one at its end), task (informal meeting-notes tasks — id, title, DRI, todo | in_progress | done, source_meeting_id; upserted from meeting payloads, and what pm/eval/report.py grades from, with board leaf tasks as the fallback), document.
  • Additive tables — issue/issue_dependency are created at runtime by JiraRepository, and activity by ActivityManager, without bumping the schema version.
  • Two DBs per run — world.db (live) and seed.db (immutable initial snapshot, used for reset and grading diffs by pm/eval/report.py).

Scenarios — pm/scenarios/

A scenario module exposes build(run_id, seed, root, force, member_persona) → Env plus MEMBERS, PROJECT_ID, and optionally agent_review_hook(env). The shared runner (scenarios/runner.py) builds a WorkDriver, installs it as the ActivityManager completion hook, sweeps once at kickoff, and runs the week with an on_tick of the PM review hook only — the closes ride the Engine's on_event_done hook — then fires one final PM close-out for work finishing on the last tick.
