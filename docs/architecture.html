PM Simulation — Architecture

A deterministic, SQLite-backed simulation of a software team's work week (Mon 09:00 → Fri 17:00). NPC coworkers work a Jira board over simulated time; a PM agent-under-test observes and steers them through Slack.

1. Overview & repo layout

Everything lives under pm/. The design has three central invariants:

  • SQLite is the single source of truth. Each run owns runs/<id>/world.db (live state) plus an immutable seed.db snapshot, so runs are replayable and gradable.
  • Only the engine mutates the world. All writes go through the typed Store, driven either by Engine.perform_action (agent tools) or by an event's start()/done() hooks.
  • Determinism. Event ordering is (start_tick, seq), NPC randomness is seeded, and time only moves through the engine — never a background thread.

3. The clock pm/sim/clock.py

Sim-time is measured in integer ticks — one tick is one simulated minute — persisted in meta.current_tick, so time survives save/resume and is fully decoupled from wall-clock (one agent action may cost many ticks regardless of how long the model took to decide).

The calendar is work-hours only: time exists during 09:00–17:00 on weekdays. Nights and weekends don't exist in tick space — 17:00 rolls straight into the next 09:00, so a delay that crosses 5pm lands the next morning automatically.

  • Module helpers — hours(n), days(n), weekday(tick), hh_mm(tick), is_within_week(tick), format_tick(tick) → "Wed 14:30".
  • SimClock(store) — now() reads the tick, advance(delta) writes it (delta must be non-negative: time never runs backwards), as_clock_str() renders it. The only mover of the clock is the engine.

4. Events pm/sim/events.py

An Event is the unit of asynchronous activity: everything durative in the world — chat latency, meetings, ticket work, being out of office — is one Event object with a uniform lifecycle and exactly one row in the event table (completion is a status flip on that row, not a second record). The engine rehydrates the right subclass from a DB row via EVENT_REGISTRY.

The complete set of event types

Only these seven types exist — nothing else may be scheduled (EventType enum → concrete class via EVENT_REGISTRY):

Scheduler & calendar (contention)

Scheduler — pm/sim/scheduler.py

  • The event table is the queue — no parallel in-memory heap.
  • schedule(event) rejects past start ticks, stamps a monotonic seq (resumed from max_event_seq()+1) and created_tick, persists, then calls calendar.reserve.
  • Queue order is (start_tick, seq) — deterministic across replays.

Calendar — pm/sim/calendar.py

  • Durative events occupy their people in the occupancy table; a meeting occupies all attendees + organizer, work occupies its single actor.
  • Yield: the incoming event's start is pushed past any overlapping block of ≥ priority.
  • Bump: lower-priority overlaps lose — an active one pauses and resumes (duration += incoming.duration); a pending one moves after the window and re-reserves recursively.
  • All resolution happens at reserve time — the engine has no runtime preemption. Instantaneous events reserve nothing and are never blocked.

5. Sim work: the sync / async boundary pm/sim/engine.py

The engine owns time progression, and this is the deliverable's central systems choice: agent actions are synchronous, the world is asynchronous — but both move the same single clock. No background threads exist anywhere.

Synchronous — perform_action(actor, cost, effect)

The contract every agent/Jira mutation routes through:

  • Run effect() at the current tick — no sim-time passes while it runs.
  • Log an action entry for the actor.
  • advance(cost) — then return the events that transitioned during the advance, so the caller observes what the world did in response.

Asynchronous — step()

Advance exactly one simulated minute:

  • start() every pending event whose start_tick has arrived,
  • then done() every active event whose duration has elapsed (freeing its occupancy blocks),
  • then activities.tick(now) for the durative-activity system.

advance(minutes) just loops step(); an instantaneous event starts and finishes within one tick.

The week loop — pm/sim/simulation.py

while not sim.is_over():          # now < WEEK_END_TICK (2400)
    on_tick(sim)                  # hooks read state + schedule(); must not advance time
    sim.step()                    # engine advances one minute
# terminal "week.end" log → RunSummary(final_tick, events_fired)

Simulation adds week guardrails on top of the engine: events that would start at or after Fri 17:00 are dropped (logged as event.dropped_past_week), and perform_action costs are clamped to the remaining week.

6. Activities pm/sim/activity.py

An Activity is a second, self-contained durative-work system that coexists with Events. Where an Event is a scheduled world occurrence (a calendar item with a fixed window), an Activity is a thing one or more NPCs are doing right now — it burns down minute by minute, can be interrupted by something more important, and resumes with its remaining time frozen. It owns its own activity table (created idempotently by ActivityManager) and never references a Task or Jira issue; effects are kind-specific side effects on start/done.

Manager rules (ActivityManager): each NPC is in at most one started activity across all attenders; dispatch runs highest-priority first; an incoming activity waits if any attender is already in an equal-or-higher-priority activity, and interrupts strictly-lower ones (every activity is interruptible). Priority is the only per-kind knob besides the two effect hooks — adding a kind is one registration in ACTIVITY_KINDS.

In practice the scenario catalog is driven by the Event system (scheduler + calendar); the Activity system is wired into every Engine.step() but stays idle until something calls activities.request(...).

How traits become behavior

Pickup hooks — pm/npc/behavior.py

Per-tick on_tick hooks that decide which work to enqueue:

  • assignee_pickup_hook — each person works their next ready assigned issue (what runner.drive uses); dev_pickup_hook — idle devs take the next ready issue in their discipline.
  • _next_issue — an issue at priority ≤ 0 (a PM “pick up” directive) overrides everything; else freestyle picks seeded-random (Random(f"{seed}:{pid}:{now}")), else by priority.
  • _dispatch_work — schedules a JiraTicketEvent (duration = estimate_minutes, auto_close from the persona) plus an optional SlackSendEvent status if announces_progress.
  • compose(*hooks) — combines several hooks into one on_tick.

Reactions — pm/npc/reactions.py

One handler per EventType, fired when an event completes (react_on_tick dispatches for everything in events_done_at(now)):

  • JIRA_TICKET done → the assignee picks up their next ready ticket (carrying their board-update policy) — work chains.
  • MEETING done → a standup prompts attendees to close their in_review work.
  • SLACK_SEND done → a message naming a person closes their in_review work; a “pick up KEY” directive bumps that issue to priority 0.
  • Email/Slack reads and OOO are documented no-op placeholders.

8. The PM agent ↔ the sim pm/agent/

The PM cannot touch the board directly. Its only mutation is Slack — and the world already reacts to Slack (reactions._on_slack_send), giving the agent exactly two levers:

  • Close: a message naming a person closes their finished-but-unclosed (in_review) work — which can unblock a teammate's dependent ticket.
  • Direct: “please pick up KEY next” bumps that issue to priority 0 — the level even a freestyle persona works first.

9. Persistence & scenarios

Store & schema — pm/db/

Database is the only module touching sqlite3 (Row factory, foreign keys ON, WAL, online backup_to). Store is the single typed interface on top — no raw SQL leaks past it. Schema (version 2) highlights:

  • Sim machinery — meta (KV: current_tick, seed, scenario), event (the durative queue itself, indexed on (status, start_tick, seq)), event_log (append-only trace), occupancy (per-person calendar blocks).
  • World entities — person (persona JSON, delay bounds), project, channel/message, email thread tables, meeting/meeting_attendee, transcript (available_tick gates discoverability), document.
  • Additive tables — issue/issue_dependency are created at runtime by JiraRepository, and activity by ActivityManager, without bumping the schema version.
  • Two DBs per run — world.db (live) and seed.db (immutable initial snapshot, used for reset and grading diffs by pm/eval/report.py).

Scenarios — pm/scenarios/

A scenario module exposes build(run_id, seed, root, force, member_persona) → Env plus MEMBERS, PROJECT_ID, and optionally agent_review_hook(env). The shared runner (scenarios/runner.py) composes the hooks — the PM hook runs first, so a same-tick close/directive lands before the person it steers picks their next ticket — runs the week, then fires one final PM close-out for work finishing on the last tick.

A procedural alternative lives in scenarios/generator.py + builders/: each EventBuilder owns exactly one EventType and fabricates unscheduled events at a chosen intensity (Level ∈ few | frequent | aggressive), with the OOO builder running first so its occupancy is reserved before anything else is placed.
