A World Model for Evaluating PM Agents

One simulated team-week, realistic where it counts — measurable where it matters.

The sim reproduces the slice of reality a PM operates in — a calendar, a board, coworkers with habits, meetings where the truth lives — and gives an LLM agent a real PM's only move: read the room, then send a message. The week is deterministic and its unmanaged outcome is pinned, so the agent's score is a clean lift over doing nothing.

The realistic setup

Real calendar time

The week runs on a real clock: 1 tick = 1 minute, 09:00–17:00, Mon–Fri. A meeting pauses whatever you were doing, and the work resumes with its remaining minutes intact — so interruptions cost exactly what they cost, never more.

Honest capacity math

Boards are tuned to real capacity: a 52 h board vs 33.5 h of working time solo once standups and a Tuesday OOO come off the calendar, or a zero-slack week per DRI on the team board — so every slip has a cause.

Coworkers with habits

Every coworker works their board a different way: perfect closes work on finish, heads_down parks it in review until asked, free_spirit picks at seeded random — so stalled handoffs aren't scripted, they emerge from the habits colliding.

Information conflict

The Jira board and the meeting notes are allowed to disagree: in one week, 25 tasks live only in transcripts while the board stays empty all five days — so the dashboard can lie, and only a PM who reads the room sees the real project.

The PM steers, never builds

The agent acts through communication and board hygiene: send_slack (naming a person closes their parked review; "please pick up KEY" preempts them onto that ticket), create_jira_ticket / update_jira_status to make the board reflect reality, and an append-only per-run memory.md — each transcript reads once, so takeaways must be banked. It can never do the engineering work itself, only steer the people who do.

Persisted & replayable

Every run is plain state: one SQLite world.db plus an immutable seed.db snapshot, auditable with the stock sqlite3 CLI. Same seed, same week, minute for minute — so a finished run can be inspected, diffed against its seed, and replayed at any time.

The evaluation harness

Each scenario engineers one failure mode, pins its unmanaged baseline (seed 42), and leaves headroom only the PM levers can recover. A do-nothing PM lands exactly on the baseline.

How the agent is scored: the same seeded week runs with and without the PM, and pm eval compares outcomes — done/total project tasks from ground truth (the informal task table, board fallback), the PROJECT DONE verdict, and hours of tickets closed. The agent's score is its lift over the pinned baseline; messages, reads, and token spend earn nothing by themselves (cost is reported beside the outcome, not blended into it), and because the week is deterministic, every point of lift is attributable to the agent's messages — never to noise.

Challenges encountered

Practical problems hit while building and running the LLM-PM sim, and what we did about them.

1 · Slow model round-trips

A single review round-trip took 60s+ with openai/gpt-5.5-pro — a sim week blocks on 2-3 round-trips per review, ~30 reviews a week, so runs were unusably slow. Switched the default to anthropic/claude-opus-4.8 (~8.6s); the wall-clock llm_request/llm_call stamps in the run logs (and examples/run_agent_llm.py) measure any model standalone.

2 · The stateless agent repeats itself

Each review starts a fresh agent with no memory: it re-read the same transcripts every 4 hours and re-created Jira tickets it had already filed. Fix: an append-only memory.md injected into every review's prompt, plus read-once, same-day transcripts — later reads return an error pointing the model at its memory.

3 · Filed tickets drop the notes' durations

The meeting notes carry an Estimate column per task, but the agent filed tickets with only a title and assignee — estimate_minutes silently fell back to the 60-minute tool default, so every ticket landed as 1h and the closed-hours metric under-counted the recovered work. Fix: the tool schema documents the fallback and the scenario prompt requires carrying over the estimate from the notes on every filed ticket.

Scope, honestly: one week of execution dynamics — picks, handoffs, reviews, visibility. No scope negotiation or estimation error, by design: it isolates the read-the-room-then-nudge loop a PM agent must master.
